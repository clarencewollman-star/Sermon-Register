# Sermon Register — Application Architecture

Status: architecture baseline for implementation
Last updated: 2026-08-17

## Purpose and document boundaries

Sermon Register is a private, self-hosted web application for recording, finding, and reusing information about Lehr and Gebet services.

This file is the source of truth for application behavior, data, privacy, storage, and the staged implementation plan. The separately uploaded Tesla-inspired design document remains the visual design reference for such matters as layout, spacing, typography, color, and interaction feel. It is not the application architecture or database specification. If the two documents conflict on behavior or data, this file governs; visual details should be reconciled without changing the data model accidentally.

## Confirmed requirements

- The application is private and is not a public website.
- It will run as a self-hosted Next.js web application, initially during local development and eventually on the owner's server.
- It must work in a browser on Windows and iPhone.
- Core data and file storage must not depend on subscription services.
- SQLite is the database.
- Songs, Texts, Vorraden, and People are reusable master records.
- Every service has exactly one Text.
- A Lehr can continue through multiple Gebets before it is finished.
- A Gebet may be linked to at most one Lehr continuation.
- Services (including Lehr services) and Vorraden can each have multiple PDF attachments.
- Search must support old sermons and reuse of records from prior years.
- Future AI retrieval must disclose only the minimum relevant records; AI is not part of the current implementation.
- The application should remain maintainable by a person without extensive programming experience.

## Architecture

```text
Windows browser / iPhone browser
              |
          private HTTPS
              |
       Next.js application
       (UI + server actions/API)
          /             \
      SQLite         private files
 sermon-register.db    uploads/
          \             /
             backups/
```

### Recommended stack

- Next.js with TypeScript for the responsive interface and server-side application logic.
- SQLite for relational data, constraints, transactions, and straightforward backup/transfer.
- Drizzle ORM and versioned migrations. Drizzle is preferred for a small, explicit SQLite schema and keeps deployment relatively simple.
- Local filesystem storage for PDFs. The database stores metadata and an opaque relative storage key, never the PDF bytes.
- A single Node.js process/container for the application. The database and uploads must be mounted as persistent data outside an ephemeral application image.
- A reverse proxy providing HTTPS when deployed. Private network or VPN access is preferred; direct public exposure is not required.

No hosted database, hosted file store, search service, or other subscription dependency is part of the core design. Source code and migrations may be stored in GitHub, but the live database, uploaded PDFs, secrets, and backups must never be committed.

### Application boundary

Browsers never read SQLite or files directly. All reads, writes, searches, and downloads pass through authenticated server-side handlers. PDF downloads use authorization-checked routes and do not expose the uploads directory as public static content.

SQLite should use foreign keys, WAL mode, a busy timeout, and short transactions. This design assumes a small private installation with modest concurrent use. If usage later outgrows a single application instance, migration to a client/server database is possible but is not a version-one concern.

## Data conventions

- Primary keys are UUID/ULID text values generated by the application.
- Dates are stored as ISO calendar dates (`YYYY-MM-DD`) because a service is a dated event, not a timestamp.
- Timestamps are UTC ISO-8601 strings and include `created_at` and `updated_at`.
- Reusable master records use `active` rather than deletion when they have history.
- Notes are plain text in version one.
- User-entered titles and names retain their original spelling; normalized companion values may be added for matching.
- Foreign-key deletion defaults to `RESTRICT`; attachments may cascade only when their owning record is deliberately deleted through an audited application operation.

## Finalized database schema

The following is the logical schema. Exact migration syntax may use SQLite `CHECK` constraints and indexes to enforce it.

### `services`

| Column | Type | Rules |
|---|---|---|
| `id` | text | primary key |
| `service_date` | text | required ISO date |
| `service_type` | text | required; `LEHR` or `GEBET` |
| `song_id` | text | required FK to `songs` |
| `song_by_person_id` | text | required FK to `people` |
| `text_id` | text | required FK to `texts` |
| `text_by_person_id` | text | required FK to `people` |
| `vorrade_id` | text | nullable FK to `vorraden`; Lehr only |
| `vorrade_by_person_id` | text | nullable FK to `people`; Lehr only |
| `lehr_status` | text | Lehr: `IN_PROGRESS` or `FINISHED`; Gebet: null |
| `notes` | text | nullable |
| `created_at` | text | required UTC timestamp |
| `updated_at` | text | required UTC timestamp |

Rules:

- Exactly one Text, Song, Song By person, and Text By person are required for every service.
- Gebet rows must have null `vorrade_id`, `vorrade_by_person_id`, and `lehr_status`.
- Lehr rows must have `lehr_status`; Vorrade and Vorrade By remain optional unless the open decision below makes them required.
- When `vorrade_id` is null, `vorrade_by_person_id` must also be null.
- A service date need not be unique; the schema permits more than one service on a date.

### `songs`

| Column | Type | Rules |
|---|---|---|
| `id` | text | primary key |
| `song_number` | text | required |
| `title` | text | nullable |
| `notes` | text | nullable |
| `active` | integer | required boolean, default true |
| `created_at` | text | required |
| `updated_at` | text | required |

`song_number` is text rather than numeric so leading zeros, suffixes, or alternate numbering remain possible. It is unique in version one; if multiple hymnals are later needed, uniqueness becomes `(hymnal_id, song_number)`.

### `texts`

| Column | Type | Rules |
|---|---|---|
| `id` | text | primary key |
| `title` | text | required |
| `scripture_reference` | text | nullable |
| `text_information` | text | nullable |
| `notes` | text | nullable |
| `active` | integer | required boolean, default true |
| `created_at` | text | required |
| `updated_at` | text | required |

A Text is reusable and does not contain service dates or completion state.

### `vorraden`

| Column | Type | Rules |
|---|---|---|
| `id` | text | primary key |
| `title` | text | required |
| `notes` | text | nullable |
| `active` | integer | required boolean, default true |
| `created_at` | text | required |
| `updated_at` | text | required |

### `people`

| Column | Type | Rules |
|---|---|---|
| `id` | text | primary key |
| `name` | text | required |
| `notes` | text | nullable |
| `active` | integer | required boolean, default true |
| `created_at` | text | required |
| `updated_at` | text | required |

The same People table supplies Song By, Text By, and Vorrade By choices. New people can be created within the service-entry flow.

### `lehr_gebet_links`

| Column | Type | Rules |
|---|---|---|
| `id` | text | primary key |
| `lehr_service_id` | text | required FK to `services` |
| `gebet_service_id` | text | required FK to `services`; unique |
| `sequence_number` | integer | required, greater than zero |
| `notes` | text | nullable |
| `created_at` | text | required |

Constraints:

- `(lehr_service_id, sequence_number)` is unique.
- `(lehr_service_id, gebet_service_id)` is unique.
- `gebet_service_id` is unique, so a Gebet cannot continue more than one Lehr.
- The two service IDs must be different.
- Application logic, inside a transaction, verifies that the parent is a Lehr and the child is a Gebet. SQLite cannot express this cross-row type rule with an ordinary `CHECK`; migration triggers may additionally enforce it.
- Links are ordered and represent all Gebets used while working through a Lehr, not merely the final Gebet.
- `services.lehr_status` is the authoritative completion flag. Changing it to `FINISHED` is explicit; the presence of links alone does not imply completion.

### `service_attachments`

| Column | Type | Rules |
|---|---|---|
| `id` | text | primary key |
| `service_id` | text | required FK to `services` |
| `original_file_name` | text | required display name |
| `storage_key` | text | required and unique, opaque relative key |
| `mime_type` | text | required; PDF only in version one |
| `byte_size` | integer | required, non-negative |
| `sha256` | text | required |
| `description` | text | nullable |
| `created_at` | text | required |

Attachments are allowed on any service, including Lehr. This is more consistent and simpler than creating a Lehr-only storage mechanism.

### `vorrade_attachments`

Same metadata columns as `service_attachments`, with required `vorrade_id` instead of `service_id`. Separate tables provide real foreign keys and avoid ambiguous polymorphic ownership.

### Authentication tables

Authentication is required, but its exact implementation remains open. If credentials are stored locally, use a `users` table containing an ID, unique login name, password hash, active flag, and timestamps. Never store plaintext passwords. The initial application may support a single administrator, while preserving a path to multiple accounts.

### Recommended indexes

- `services(service_date DESC)`
- `services(service_type, service_date DESC)`
- indexes on every service foreign key
- `lehr_gebet_links(lehr_service_id, sequence_number)`
- case-insensitive lookup indexes for person name, Text title/reference, Vorrade title, and Song number/title
- attachment owner indexes

Version-one search can use indexed filters plus SQLite FTS5 for titles, scripture references, informational text, and notes. FTS is local and requires no search service. Build it only after basic CRUD and filtering are correct.

## Relationships

```text
songs 1 --------< services >-------- 1 texts
                       |
                       +---- song_by --------> people
                       +---- text_by --------> people
                       +---- vorrade_by -----> people
                       |
vorraden 1 ------< Lehr services
    |                  |
    |                  +----< service_attachments
    |
    +----< vorrade_attachments

Lehr service 1 ----< lehr_gebet_links >---- 1 Gebet service
                     (ordered; Gebet unique)
```

One Song, Text, Vorrade, or Person can therefore be reused by many service occurrences without copying its master data. Notes on a reusable record describe that record; notes on a service describe that particular occurrence.

## File storage and backup

Suggested deployment layout:

```text
sermon-register/
  app/                         application release
  data/
    sermon-register.db
    uploads/
      services/<service-id>/<opaque-id>.pdf
      vorraden/<vorrade-id>/<opaque-id>.pdf
    backups/
```

- Validate MIME signature as well as extension, limit file size, generate storage names server-side, and prevent path traversal.
- Upload to a temporary file, calculate the hash, then move it into place and commit its metadata. Compensate cleanly if either filesystem or database work fails.
- Downloads use an authorization check and safe `Content-Disposition` headers.
- A backup is not complete unless it contains a transactionally consistent SQLite snapshot and all uploaded files.
- Automate dated backups, retain multiple generations, and periodically test restoration on another directory/machine.
- Keep encryption keys and passwords outside the repository. Full-disk or backup encryption is recommended for private material.

## Private access and security

- Require login before any application page, API action, search result, or PDF download.
- Prefer access over the owner's private LAN or a self-hosted/private-network VPN. If internet-facing access is later chosen, require HTTPS, rate limiting, secure cookies, CSRF protection, strong credentials, and timely system updates.
- Authorization is enforced server-side on every operation. UI visibility is not a security boundary.
- Do not put the database, uploads, backups, environment files, or logs containing private content in GitHub.
- Record only operational metadata in logs; avoid service notes, PDF contents, and search queries where possible.
- Initial deployment should run one application instance against the SQLite file on local server storage, not on a network filesystem.

## User experience

The Windows register should provide a fast table-like view with sorting, filters, keyboard-friendly editing, searchable reusable-record selectors, and an inline “add new” action. It should feel spreadsheet-like without behaving like an unvalidated spreadsheet.

The iPhone interface should use a responsive list and focused edit form instead of squeezing all columns into a grid. Both interfaces use the same records, validation, and server operations.

Core screens:

1. Sign in.
2. Service register with search and filters.
3. Add/edit service, adapting fields for Lehr or Gebet.
4. Service detail with PDFs and Lehr continuation history.
5. Reusable Songs, Texts, Vorraden, and People lists/details.
6. In-progress Lehr view for linking ordered Gebets and marking completion.
7. Backup/health information for the administrator.

## Future privacy-preserving AI retrieval (not in current scope)

The future AI feature must not receive a database export, unrestricted database connection, entire PDF library, or unrelated records. The intended boundary is:

```text
question
   -> authenticated local retrieval service
   -> narrow search/filter over permitted records
   -> small, cited context bundle
   -> optional AI provider or local model
   -> answer with links/citations back to source records
```

Preparation now is limited to clean relational data, stable IDs, attachment metadata, and a retrieval boundary. Do not add embeddings, a vector database, automated PDF extraction, or an AI provider in the initial stages. Before any future AI implementation, decide whether processing must remain wholly local; if an external model is considered, require explicit opt-in, a visible preview of the material being sent, redaction/minimization, and documented retention controls.

## Staged development plan

### Stage 0 — settle open decisions and preserve references

- Keep this file as the architecture source of truth and the uploaded Tesla-inspired document as the separate visual reference.
- Resolve the open decisions below that affect authentication, validation, and deployment.
- Define a small acceptance checklist using representative Lehr/Gebet histories.

### Stage 1 — project and data foundation

- Create the Next.js/TypeScript project, Drizzle schema, migrations, seed data, and local persistent directories.
- Implement all constraints and tests, especially service-type rules and ordered Lehr/Gebet links.
- Add environment configuration and repository exclusions for private data.

### Stage 2 — reusable records

- Build create, edit, search, activate/deactivate, and history views for Songs, Texts, Vorraden, and People.
- Add searchable selectors and inline creation.

### Stage 3 — service register

- Build responsive Windows table and iPhone list/form experiences.
- Add Lehr/Gebet-specific validation, filters, sorting, and service detail/history.
- Support ordered Gebet links and explicit Lehr completion.

### Stage 4 — private PDFs

- Add multi-PDF upload, list, download, rename/describe, and deliberate removal for services and Vorraden.
- Add signature/size validation, opaque paths, hashes, and authorization tests.

### Stage 5 — search and usability

- Add combined filters and then FTS5 if needed.
- Add reuse history, “last used,” in-progress Lehr views, keyboard flow, and mobile polish.
- Apply and verify the Tesla-inspired visual system without changing the architecture.

### Stage 6 — authentication, deployment, and recovery

- Complete the chosen local authentication method.
- Deploy one instance to the owner's server behind private HTTPS access.
- Automate database-plus-upload backups and complete a documented restore test.
- Add update, migration, and troubleshooting instructions for a non-expert maintainer.

### Stage 7 — future retrieval preparation

- Only after the core register is stable, specify an auditable, least-data retrieval interface.
- AI implementation remains a separate, explicitly approved project.

## Open decisions

These are intentionally unresolved; none requires redesigning the core schema unless noted.

1. **Authentication and users:** single owner account or multiple named users? This determines local user administration and whether future per-user audit/permissions are needed.
2. **Remote access:** private LAN only, a private VPN, or an internet-facing domain? This determines reverse-proxy and hardening details.
3. **Lehr continuation semantics:** confirmed assumption for this design: every linked Gebet participates in continuing one Lehr, and the Lehr is separately marked finished. Confirm whether the final Gebet must be explicitly identified; if yes, add `completes_lehr` to the link with at most one true link per Lehr.
4. **Required participants:** are Song By and Text By always known at entry time? They are modeled as required; make them nullable if incomplete historical entries must be saved.
5. **Vorrade rules:** can a Lehr omit a Vorrade, and when a Vorrade exists must Vorrade By exist? Both are currently optional as a pair.
6. **Text PDFs:** current scope attaches PDFs to service occurrences and Vorraden, not reusable Text records. Confirm whether reusable Texts also need their own PDFs; if so, add an explicit `text_attachments` table.
7. **Song identity:** song number is assumed unique in a single songbook. If multiple hymnals/songbooks are used, add a `hymnals` table before enforcing uniqueness.
8. **Existing data import:** source format, volume, duplicate rules, and attachment naming are unknown.
9. **Deletion policy:** recommended default is deactivate master records and restrict deletion of referenced data. Confirm whether an administrator needs permanent deletion and an audit trail.
10. **Server platform:** operating system, container preference, domain, TLS method, and backup destination remain deployment choices.

## Explicitly out of scope for the first release

- AI chat, embeddings, vector databases, or sending records to an AI provider.
- Public registration or public pages.
- Cloud database/file subscriptions.
- Multiple application instances sharing one SQLite database.
- Native Windows or iPhone applications; the responsive web application serves both.
- Full document-management workflows, PDF editing, or OCR unless separately approved.
